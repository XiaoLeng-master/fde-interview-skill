# 国内企业交付 Case Bank

## 使用规则

只向候选人展示 Initial Brief。隐藏证据按候选人的问题逐条释放。每轮只回答当前问题并提出一个自然追问；不要替候选人完成 Discovery。

## Case 1：制造设备维修知识 Agent

### Initial Brief

一家制造企业希望 4 周内上线设备维修知识 Agent，让一线维修人员输入故障描述即可获得处理建议。领导认为知识都在 PDF 手册里。

### 隐藏证据

- 问用户：领导说服务所有工厂；实际首批是一个工厂 18 名维修人员。
- 问流程：员工先拍照发微信群，再找班组长；手册通常最后才看。
- 问知识：PDF 有三个版本，部分扫描件；老师傅经验不在文档中。
- 问异常：错误建议可能造成停线或安全事故。
- 问基线：没有准确率；有近三个月维修工单、平均首次响应 42 分钟。
- 问系统：工单系统有只读 API，写入需要 IT 审批；现场网络不稳定。
- 问权限：设备安全操作必须由有资质人员确认。
- 问 Owner：设备主管负责响应时间；EHS 负责安全边界；IT 接收运行。

### 期待范围

第一阶段只做故障归类、证据检索和相似工单推荐，不自动下达高风险操作；覆盖两类高频设备；引用来源，班组长确认后写回工单。

### 评分点

- 是否发现真实入口是微信群/照片/班组长，而非 PDF Chat。
- 是否建立版本、OCR、专家知识和权限策略。
- 是否用首次响应、建议接受、错误严重度和人工接管评测。
- 是否考虑弱网、审计、资质确认、回滚和运营。
- 是否沉淀设备类型模板、文档处理和工单连接器。

### 追问

- 如果领导坚持全自动，你怎样回应？
- 老师傅不愿录入经验怎么办？
- 如何避免旧版手册进入回答？

## Case 2：销售线索与 CRM 回写

### Initial Brief

一家 B2B 公司希望 Agent 自动读取销售微信群和会议纪要，提取线索、生成跟进建议并回写 CRM，目标是“销售效率提升 50%”。

### 隐藏证据

- 问用户：销售约 120 人，不同区域流程不同；管理层想看漏斗，销售担心被监控。
- 问数据：微信群无法获得稳定官方历史接口；会议纪要可导出；CRM API 有每日限额。
- 问基线：线索录入率约 55%，没有“效率”统一口径。
- 问异常：同一客户多人跟进，错误归属影响提成。
- 问动作：创建线索可撤销，修改客户 Owner 需要主管审批。
- 问 Owner：销售运营负责录入率，区域主管负责采用，IT 管 API。
- 问合规：客户联系方式属于敏感数据，不能发给外部未批准模型。

### 期待范围

先从会议纪要和企业邮件生成“待确认线索草稿”，销售确认后写入；不自动改 Owner；定义录入率、确认率、重复率、平均处理时间和投诉 Guardrail。

### 评分点

- 是否质疑“50%”并建立基线。
- 是否处理数据入口合法性、隐私、CRM 限流和幂等。
- 是否理解销售激励与采用阻力。
- 是否把高风险写操作放在审批边界。

### 追问

- 销售认为多一次确认更麻烦怎么办？
- 同一客户重复写入怎样处理？
- 如何证明是系统改善，而不是管理层同期强推 CRM？

## Case 3：金融制度问答与审批辅助

### Initial Brief

某金融机构希望建立制度问答 Agent，并逐步让它自动判断业务申请是否合规。要求私有化部署，第一阶段 6 周。

### 隐藏证据

- 问用户：初期是 60 名运营审核员，不直接面向客户。
- 问知识：制度分总部、地区和产品层，存在生效时间、废止和冲突。
- 问动作：误批存在监管风险；拒绝也会造成业务损失。
- 问权限：不同产品团队只能看本域材料；所有查询需审计。
- 问基线：当前查制度中位 12 分钟，资深审核员抽检一致率约 87%。
- 问基础设施：只能使用内网模型；GPU 有限；外部 Observability SaaS 禁止。
- 问 Owner：合规负责制度解释，运营负责流程，平台团队负责运行。

### 期待范围

首期只做带引用、版本和适用范围的检索与审核清单；不自动批准/拒绝。高风险问题转资深审核员；建立时间切片、权限过滤和审计。

### 评分点

- 是否区分检索证据、制度解释和审批授权。
- 是否处理时间版本、冲突、权限和私有化限制。
- 是否定义 Faithfulness、适用范围正确性、人工一致性和处理时间。
- 是否提供模型/检索降级、发布 Gate 和制度更新流程。

### 追问

- 制度互相矛盾时 Agent 怎么办？
- 内网模型效果不足怎么办？
- 什么时候可以从辅助升级到自动判断？

## 通用结束要求

候选人需要交付：当前流程、Stakeholder、基线、非目标、Vertical Slice、架构与 Effect Boundary、Eval、试点、发布/回滚、采用和复用。评分使用 `dual-track-rubric.md`。
