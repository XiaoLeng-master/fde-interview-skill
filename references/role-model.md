# FDE 角色模型

## 一句话定义

Forward Deployed Engineer 进入客户或业务现场，把模糊、跨系统、带组织约束的问题转成可运行、可采用、可运营的软件结果，并把现场学习反哺为下一次可复用的产品、连接器、模板或方法。

FDE 不是由 Title 决定的。判断一个人是否做过 FDE 式工作，要看证据链：

```text
真实流程 → 明确问题和边界 → 亲手实现 → 受控上线
→ 用户采用 → 可验证结果 → 运营交接 → 复用/产品回流
```

## 四项责任

1. Discovery：观察真实工作，识别操作人员、例外、系统、政策和决定权。
2. Product：决定什么值得改变、什么暂时不做、哪些判断保留给人。
3. Engineering：选择最小充分机制，打通数据、接口、权限、状态和运行链路。
4. Operation：用真实 Case 证明结果，发布、支持、回滚、推动采用并沉淀学习。

## 生命周期与最低证据

| 阶段 | 核心问题 | 最低证据 |
| --- | --- | --- |
| 继承需求 | 需求是否只是未经验证的假设？ | 原始 Brief、假设与未知项 |
| 观察现场 | 工作实际上怎样发生？ | 代表性 Case、异常、操作人员、系统和绕行方式 |
| 定义价值 | 什么变化才算成功？ | 基线、目标人群、Owner、Verifier、Guardrail |
| 选择机制 | 是否真的需要模型或 Agent？ | 确定性软件、检索、模型、Agent、人工的取舍 |
| 垂直切片 | 能否跑通一条真实关键路径？ | 真实/近真实数据、工具、状态、失败路径 |
| 受控试点 | 能否在有限风险下使用？ | 试点人群、权限、人工复核、Eval、退出条件 |
| 生产上线 | 系统能否被支持和撤回？ | 日志、审计、SLO、Runbook、发布门禁、回滚 |
| 采用运营 | 用户是否稳定改变了工作方式？ | 使用、接受、修正、业务事件和负责人证据 |
| 复用回流 | 下一次交付是否更便宜、更快或更安全？ | 连接器、模板、Skill、平台能力或产品 Backlog |

## 与相邻角色的区别

岗位名称没有统一标准，按实际责任判断。

| 角色 | 常见重心 | 与 FDE 的交集/差异 |
| --- | --- | --- |
| Software Engineer | 内部产品、平台或服务 | 工程深度可迁移；通常较少直接拥有客户采用和现场范围 |
| AI/Agent Engineer | 模型应用、RAG、Agent、Eval | 技术高度重叠；FDE 还需客户发现、交付、价值与组织采用 |
| Solutions Engineer | 售前 Demo、方案、技术支持 | 客户沟通重叠；部分公司也写生产代码，需看责任而非 Title |
| Solutions Architect | 架构设计、平台采用、治理 | 系统设计重叠；FDE 往往更强调亲手实现和快速迭代 |
| Implementation/Delivery | 配置、集成、项目上线 | 交付重叠；若没有产品回流和复用，仍可能是一次性项目制 |
| Consultant | 问题分析、流程与组织建议 | Discovery 重叠；FDE 必须能把结论落实为可运行系统 |
| Deployment Strategist | 业务问题、组织推动和价值 | 常与 FDE 配对；工程深度和 Title 因公司而异 |

## 常见 FDE 类型

- AI/Agent FDE：Agent 工作流、RAG、Evals、工具、权限和生产化。
- Data/Platform FDE：数据集成、语义层、平台应用、治理和客户扩展。
- Enterprise Workflow FDE：连接 CRM、ERP、工单、审批和内部工具。
- Field/Edge FDE：硬件、网络、边缘环境、现场调试和高可靠运行。
- Privacy/Security FDE：合规边界、数据映射、策略执行和安全集成。

## 国内企业交付轨

常见额外约束：流程依赖微信/Excel/PDF、系统 API 不完整、数据口径不一致、决策链复杂、PoC 周期短、私有化或本地模型要求、预算与采购不确定。面试重点通常包括：能否进入现场、快速切范围、亲手集成、向业务解释价值并在有限条件下交付。

## 国际/平台型轨

常见额外要求：英文客户沟通、Coding 与 System Design、API/Cloud/Data/AI 平台深度、Multi-tenant/RBAC/Audit/SLO、跨时区协作，以及把一线模式 upstream 到核心产品。面试可能组合 Coding、Debugging、Architecture、Customer Case 和 Behavioral。

## 证据强度

从弱到强：

1. 听说或了解概念。
2. 独立 Demo。
3. 用接近真实的数据跑通关键路径。
4. 有限定用户、人工复核和运行数据的试点。
5. 有生产发布、监控、故障与回滚责任。
6. 有独立验收的采用或业务结果。
7. 有跨客户、跨团队或第二次交付的复用证据。

面试与简历不得把低层级证据描述成高层级证据。
