# 价值、采用、交接与复用

## 价值不是 Demo 效果

输出生成、任务完成、用户接受、业务结果是四个不同层级。FDE 必须明确哪个事件由独立的人或系统证明结果被接受。

## 价值契约

至少定义：

- Eligible Population：能合法、合理使用的任务范围。
- Baseline：现状指标、时间、样本和置信度。
- Accepted Outcome：输出被业务接受的事件。
- Verifier：独立验证的人、规则或 Source of Truth。
- Target：希望改善多少、何时观察。
- Guardrails：质量、风险、成本或体验不能变差的指标。
- Attribution：如何排除同期其他变化。
- Full Cost：发现、开发、模型、工具、人工、支持、事故和维护。
- Owner：谁对指标和继续/停止决定负责。

示例：

```text
每个已接受结果成本 = 生命周期与运行总成本 / 被独立接受的结果数
```

不要把试点预测、演示结果和生产实现价值混在一起。

## 采用计划

上线不等于采用。至少说明：

- 从哪些用户开始，为什么；
- 系统嵌入哪个现有工作界面；
- 培训、Office Hour 和反馈渠道；
- 什么情况下人工接管；
- 业务负责人如何检查使用与结果；
- 扩展、暂停和退出条件；
- 岗位、审批或激励是否需要改变。

## 采用失败诊断

如果质量好但没人用，依次检查：

1. 是否选错任务或用户。
2. 是否增加额外步骤，而不是减少摩擦。
3. 用户是否信任数据、解释和责任边界。
4. 失败时是否容易修正或转人工。
5. 管理者的目标与操作人员的激励是否一致。
6. 是否存在更快的非正式绕行流程。

## 交接与运营

Receiving Team 必须知道：服务边界、版本、依赖、SLO、告警、常见故障、升级路径、Kill Switch、数据和权限 Owner、成本预算、变更流程和退役条件。培训材料不能替代真实 On-call 与决策权。

## 复用分类

- 客户专属配置：留在客户边界，不强行产品化。
- 行业可选能力：模板、Extension、Ontology、Policy Pack。
- 多客户稳定共性：连接器、SDK、Skill、平台能力或产品基线。

决定是否沉淀：同类需求数量、稳定共性、维护成本、风险和真实二次采用。文档数量不是复用结果。

## 面试题

### Q1：项目成功指标是什么？

高分回答包含业务接受事件、Verifier、基线、Guardrail、成本和 Owner。只报模型准确率或调用量不够。

### Q2：上线后用户不用怎么办？

观察真实流程和摩擦，区分质量、信任、界面、激励、培训和任务选择；与 Owner 决定重构、收缩或停止，而不是单纯加培训。

### Q3：如何证明节省了 30% 时间？

追问口径：谁、哪些任务、前后窗口、样本、是否包含人工复核、同期变化、数据负责人和置信度。无法回答则不能使用该百分比。

### Q4：什么时候应该停止 AI 项目？

没有 Owner/Verifier、数据修复超过价值上限、风险无法受控、采用无法建立、全成本后价值为负，或更简单方案足够。

### Q5：如何把一次交付变成产品能力？

收集重复失败/需求证据，分离客户配置与稳定共性，定义接口、版本、Owner、兼容和第二个验证客户，再进入产品基线。

### Q6：客户续约是否证明系统有价值？

不一定。续约可能由打包合同、关系或切换成本驱动。仍需查看采用、接受结果、业务 Guardrail、全成本和替代方案。

## 复用检验

```text
第二个客户/团队是否实际使用？
交付时间、成本或风险是否下降？
谁维护这个资产？
客户特有信息是否被安全隔离？
失败 Case 是否进入产品 Eval 或 Release Gate？
```

## 反面信号

- 用使用次数代替接受结果。
- 只算 Token，不算人工复核和支持。
- 把预测 ROI 写成已经实现。
- 用户不用就归咎于“抗拒变化”。
- 所有客户定制都合入核心产品。
- 项目结束没人接手，却声称已规模化。
