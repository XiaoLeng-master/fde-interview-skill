# 目标岗位尽调

## 目标与边界

在候选人投递、面试或接受岗位前，根据 JD、公司商业模式、产品材料、客户案例、团队信息和面试记录，判断岗位的真实运行模式。不要根据 Title 判断，也不要把驻场、全栈、生产代码、私有化部署、大客户、高薪或“反哺产品”等单一表述当成充分证据。

本模块判断岗位和组织，并把结果交给准备度诊断、简历、模拟面试或 Case Drill。它不替雇主评价候选人，不预测录用概率，也不替用户作出投递或 Offer 决策。

## 输入与证据等级

优先提取用户已经提供的材料，不重复询问能够直接获得的信息。可使用 JD、官网、财报、产品资料、客户案例、招聘或面试口述、组织结构、代码与运行证据。材料不足时给暂定分类和最小核验问题，不强行打分。

关键判断按以下等级标记：

- **已确认事实：** 财报、正式流程、可检查的产品或仓库、生产 Trace、采用数据，或相互印证的一手来源。
- **公司自述：** 官网、JD、产品手册、招聘人员或面试官表述。
- **第三方自述：** 员工、客户、媒体或公开复盘的单方口径。
- **可辩护推断：** 根据商业模式、产品形态和组织机制推导，必须说明推断链。
- **待核验事实：** 当前材料不能回答且会改变岗位分类的问题。

涉及当前公司、客户、收入、产品或招聘流程时，核验最新一手来源并写明采集日期。低等级证据不能覆盖高等级反证。

## 诊断流程

### 1. 还原商业和组织位置

先回答客户为什么付钱：标准软件、订阅或授权、API/Token/算力用量、硬件设备、项目总包、人天驻场、行业方案，还是运维培训。继续检查：

- 收入随产品采用增长，还是随设备、项目和交付人员增长？
- 销售签的是标准能力，还是开放式定制范围？
- 软件是独立产品，还是硬件和项目的附属能力？
- FDE 位于产品研发、交付、售前、销售还是售后体系？向谁汇报？
- 项目结束后是否存在续费、用量、扩容或持续采用收入？

硬件、咨询或项目收入不自动否定 FDE，但会提高逐客定制和验收导向的风险。

### 2. 建立八维证据矩阵

每个维度记录证据、证据等级、正向信号、风险信号和缺口；未知就是未知，不用中间分填补。

| 维度 | 正向信号 | 风险信号 |
| --- | --- | --- |
| 产品底座 | 有统一版本、Roadmap、负责人、升级路径和多客户运行；差异通过配置、插件、Connector 或 Adapter 隔离 | 每客复制代码、长期分叉；“平台”只是演示或临时拼装 |
| 问题发现与范围 | FDE 接触业务 Owner 和实际用户，定义基线、非目标、验收，并能用证据调整范围 | 销售先承诺，FDE 后补方案；客户提什么就实现什么 |
| 工程责任 | 生产代码进入公司正式仓库，有 Review、测试、CI/CD、版本和维护人 | 只做配置演示；代码留在客户仓库或个人脚本；谁交付谁永久维护 |
| 生产责任 | 覆盖权限、数据、评测、Trace、成本、降级、人工兜底、发布和回滚 | 只完成 Demo、POC、安装或一次验收 |
| 采用与价值 | 有业务 Owner、使用基线、实际用户、采用指标和流程变化 | 只看模型分数、项目进度和验收；上线后使用未知 |
| 产品回流 | 现场共性进入 Backlog，由产品或研发接收并发布为受维护资产 | 只形成 PPT 或复盘；没有接收人；客户定制长期分叉 |
| 跨客户复用 | 客户 A 的资产被客户 B 使用，并降低周期、成本、故障或风险 | 只复制旧项目代码，不能说明减少了什么 |
| 组织承接与成长 | 产品、平台、交付和客户成功边界清楚；有导师和评审；驻场有退出条件；绩效包含采用或复用 | 长期绑定单客；范围无限；没有产品接收方；只考核人天、验收、销售额或投诉 |

### 3. 检查两个复利硬门槛

总分不能替代以下门槛：

1. **产品回流：** 客户现场的通用能力是否进入公司正式产品、平台、标准组件或由组织维护的知识资产？
2. **二次复用：** 上述资产是否已经被第二个客户或后续项目使用，并降低交付投入或风险？

判定：

- 两项都成立：可以判断已形成 FDE 复利闭环。
- 产品回流成立，二次复用尚未发生：可判断为早期建设型 FDE，不能声称已规模化。
- 产品回流不成立：即使技术很强，也只能归为客户交付或项目型技术工作。
- 两项都未知：只能给暂定分类；JD 愿景不能替代证据。

## 岗位分类

- **产品型 FDE：** 有持续维护的产品底座；FDE 参与问题发现、生产交付和采用；两个硬门槛均有证据。
- **早期建设型 FDE：** 已有产品或平台雏形，岗位覆盖需求、工程和生产，组织正在建立反馈与组件机制；产品回流已有机制或首例，但二次复用、导师或评价体系尚未验证。
- **项目型技术交付：** 有真实客户、生产环境和工程深度，但成功主要按范围、进度和验收衡量；资产没有稳定进入产品或跨客户复用。
- **高级外包或驻场开发：** 客户控制范围和优先级，收入依赖人天或项目，代码归客户或长期分叉，员工绑定单客，组织没有产品接收机制。
- **实施、售前或售后：** 主要安装、配置、演示、培训、工单和问题转交，很少拥有生产代码、业务采用或产品回流责任。
- **证据不足：** 无法确认商业模式、实际授权、代码归属或两个硬门槛。列出哪些事实会把分类推向不同方向。

是否驻场不是决定条件：远程逐客定制也可能是外包；驻场且形成产品回流和跨客户复用也可能是真正的 FDE。

## 候选人价值与风险

岗位分类完成后，再映射候选人，而不是反过来用候选人的偏好改变岗位事实：

- 它能补候选人的哪些 Echo 证据：现场发现、业务 Owner、范围、采用、价值？
- 它能补哪些 Delta 证据：代码、集成、部署、权限、观测、故障和回滚？
- 候选人能否接触完整闭环，还是只被分配其中一段？
- 岗位的产品、客户和生产证据能否在保密边界内转成可辩护的职业资产？
- 最大机会成本是什么：工程深度下降、长期驻场、单客绑定、无导师、无产品回流，还是与目标轨道不一致？

使用条件式结论。例如：“若能确认核心仓库权限、产品接收方和明确导师，该岗位能补生产交付证据；若代码长期留在客户项目且绩效只看验收，应把它视为项目交付，而不是产品型 FDE。”

## 核验问题

只问会改变分类的问题，并要求具体事实：

1. 能否举一个客户现场问题进入哪个产品版本、由谁接收、又在哪个后续客户复用的例子？
2. FDE 的生产代码进入公司产品仓库、客户仓库还是独立项目仓库？由谁 Review 和长期维护？
3. 客户购买的是设备、项目、人天、软件授权、订阅还是用量？它如何影响团队目标？
4. 最近三个项目的成功指标是验收、采用、业务结果还是复用？谁负责验证？
5. FDE、核心研发、产品、生态伙伴和客户团队各负责哪一层？
6. 驻场持续多久，退出条件是什么，上线后的运维和新增需求由谁承担？
7. 候选人入职前 90 天的项目、导师、代码权限和生产权限是什么？

对关键问题说明验证目标、绿色信号和红色信号。不要问“你们重视沉淀吗”这类只能得到立场、得不到事实的问题。

## 反误判检查

输出前确认：

- 没有因 Title、驻场、全栈、生产代码、私有化部署、大客户或高薪直接判为 FDE。
- 没有因驻场、客户定制、项目制或系统集成直接判为外包。
- 没有把公司拥有产品等同于岗位围绕产品工作。
- 没有把公司计划、JD 愿景、Demo 或销售成功当成产品回流和用户采用。
- 没有把候选人喜欢或需要这个岗位当成岗位质量证据。
- 允许转型期岗位被分类为早期建设型或有边界的混合态。

## 默认输出

1. **一句话判断：** 暂定类型、置信度和决定性依据。
2. **商业与组织位置：** 客户购买什么，岗位位于哪一段价值链。
3. **证据矩阵：** 八个维度分别列证据等级、判断和缺口。
4. **复利链路：** `客户问题 -> 现场产出 -> 产品接收 -> 标准版本 -> 二次复用 -> 降低投入或风险`，明确目前证明到哪一步。
5. **候选人价值与风险：** 条件式说明，不给录用概率或替用户作决定。
6. **核验问题：** 按对岗位分类和个人决策的影响排序。
7. **事实边界：** 分开已确认事实、公司或第三方自述、可辩护推断和待核验事实。

置信度依据证据覆盖判断，不输出伪精确分数。只有招聘文案或公司宣传时为低；有商业、产品、项目和组织证据但缺少硬门槛时最多为中；两个硬门槛及运行证据齐全时才可为高。
