# FDE Evidence Readiness Index 与双轨启发式

## 使用原则

FDE Evidence Readiness Index（FERI）只衡量当前材料中“可用于 FDE 求职与面试的证据准备度”。它是本仓库为候选人自查和教练反馈设计的启发式，不是能力真值、录用概率、工作表现、薪酬预测、候选人排名或任何雇主的招聘标准；阈值也未按真实录用结果校准。

先收集证据，再判断是否评分。不得因为候选人说“负责”就自动判定 Owner，也不得因为没有 FDE Title 就判零分。

## Echo 与 Delta 轴

- **Echo（现场与价值轴）**：发现并验证用户、流程、例外、约束、范围、基线、Owner、采用和价值。对应核心维度 1、4、6。
- **Delta（工程与交付轴）**：亲手把问题转成可运行、受控、可恢复的软件结果。对应核心维度 2、3。
- 维度 5 和 7 是桥接维度：分别观察两轴在模糊环境中的协同，以及现场学习能否回流复用。桥接证据不能替代任一核心轴。

## 最小证据门槛与默认输出

只有同时满足以下条件，才给总分区间：

1. 7 个维度中至少 4 个有可核验的行为或产物；
2. 至少 1 个 Echo 核心维度有证据；
3. 至少 1 个 Delta 核心维度有证据。

未越过最小证据门槛时写 **“暂不评分”**，仍逐维列出已确认事实、可辩护推断、证据缺口和补证动作。不得把空白维度直接计为零来制造低分。

越过门槛后默认输出区间而非精确点数，并附置信度：

- 高置信度：大多数关键结论有代码、文档、运行记录、独立验收或一致的多源事实支持；建议区间宽度 5–8 分。
- 中置信度：材料和回答能互相支持，但仍有若干边界待确认；建议区间宽度 9–15 分。
- 低置信度：主要依赖候选人单方概述，缺少产物或独立验证；建议区间宽度 16–25 分。

各维分档是校准锚点，不要求机械逐点相加。先按证据强度形成维度范围，再合成总范围；显著矛盾应降低置信度或改为“暂不评分”。

## 7 维启发式（参考上限 100）

### 1. 问题发现与范围界定（20）

- 0–4：只接受需求，没有验证用户、流程或指标。
- 5–9：能澄清功能，但缺少现场观察、异常或 Owner。
- 10–14：能画流程、识别 Stakeholder、非目标和关键约束。
- 15–18：能用代表性 Case、基线、Verifier 和 Guardrail 界定试点。
- 19–20：能在需求与现场冲突时用证据重构范围并获得授权。

### 2. 技术实现与系统设计（20）

- 0–4：概念或配置级，无独立实现证据。
- 5–9：完成模块或 Demo，但接口、数据和取舍较薄。
- 10–14：能独立实现端到端关键路径并解释架构取舍。
- 15–18：处理复杂集成、性能、数据一致性、扩展和调试。
- 19–20：能在陌生客户环境快速定位问题并形成稳定平台扩展点。

### 3. 生产交付与运行控制（20）

- 0–4：没有部署、测试或运行证据。
- 5–9：可部署，有基础日志和错误处理。
- 10–14：具备测试、身份权限、监控、重试、人工兜底。
- 15–18：具备发布门禁、灰度、回滚、事故响应、成本与 SLO。
- 19–20：能运营高风险或大规模系统，并用线上失败持续改进。

### 4. 业务价值与用户采用（15）

- 0–3：只有模型或技术指标。
- 4–7：有用户反馈或使用量，但缺少基线和独立验收。
- 8–11：有采用计划、业务 Owner、验收事件和 Guardrail。
- 12–14：有可归因的生产结果和完整成本意识。
- 15：能基于证据做继续、收缩、扩展或停止决策。

### 5. 模糊环境下的问题解决（10）

- 0–2：依赖完整需求和熟悉系统。
- 3–5：能拆解未知项并主动验证。
- 6–8：能处理数据、文档、系统和人员之间的冲突证据。
- 9–10：在高压力、陌生环境下仍能保护边界、推进决策并复盘。

### 6. 客户与利益相关者沟通（10）

- 0–2：只描述技术结果。
- 3–5：能向非技术人员解释方案并同步风险。
- 6–8：能主持 Discovery、管理预期、推动跨团队采用。
- 9–10：能处理高层承诺与现场现实冲突，并保持信任和进度。

### 7. 复用资产与产品反馈（5）

- 0：没有复用或反馈。
- 1–2：有文档、脚本或内部分享，但无再次使用证据。
- 3–4：形成模板、连接器、组件、Skill 或产品 Backlog。
- 5：有第二次复用或进入产品基线的证据，并降低成本、风险或周期。

## 区间解释

- 80–100：具备较完整 FDE 证据，可按目标公司做专项准备。
- 65–79：可投递，但需补一到两个高影响证据并准备好解释边界。
- 50–64：有条件投递相邻岗位；优先完成一条真实交付闭环。
- 35–49：基础可迁移，但简历直接改名风险高，先补项目与客户证据。
- 0–34：先建立工程或交付基础，不建议仅靠话术冲 FDE。

这些区间是仓库启发式，只表示证据准备状态，不是招聘承诺、录用概率或雇主标准。若目标岗位对 Coding、行业、语言、出差或安全资质有硬门槛，单独判定 Gate，不用总分抵消。

## 国内企业交付 Overlay（单独 0–20）

每项 0–4：

1. 能观察并重构低标准化的真实流程。
2. 能连接微信/飞书/Excel/PDF/ERP/CRM 等非理想系统。
3. 能在短 PoC、采购、预算和私有化约束下切范围。
4. 能和老板、业务、一线操作人员及研发共同推进采用。
5. 能把一次性交付沉淀为行业模板或可复用组件。

## 国际平台 Overlay（单独 0–20）

每项 0–4：

1. 英文 Discovery、技术解释和冲突沟通。
2. Coding、Debugging 和 System Design 深度。
3. Cloud/Data/AI 平台及 Multi-tenant、RBAC、Audit、SLO。
4. 全球客户、跨时区、文档化和独立推进。
5. 将 Field Learning upstream 为产品或平台能力。

## 证据标签

- `已确认`：简历、代码、文档、运行记录或用户回答明确支持。
- `可推断`：根据事实合理成立，但面试前仍需候选人确认。
- `证据缺口`：对岗位重要，但当前没有可辩护材料。
- `硬门槛`：不满足会直接阻断目标岗位，例如工作许可、语言、Coding 或行业资质。
